DERIVE rules derived labels by fixpoint · queries stay Virtual Cypher — that sheet still applies

What is new here A rule may reference the label it defines. Everything below is detail.

Conclusions that feed back in

Two rules, one label. The second matches :PhoenixSuccessor — the very label it concludes — so chains of any depth resolve. No single query can say this; a query has a fixed depth, a fixpoint does not.

# rules/phoenix-succession.yml
name: gov-uk/phoenix-succession
derives: PhoenixSuccessor
rules:
  - derive: "(b:PhoenixSuccessor)"
    from: |
      MATCH (a:UkAppointment {companyStatus: 'dissolved'}),
            (b:UkAppointment)
      WHERE b.officerId = a.officerId
        AND b.companyNumber <> a.companyNumber
        AND b.appointedOn > a.appointedOn
  - derive: "(c:PhoenixSuccessor {phoenixDepth: d})"
    from: |
      MATCH (b:PhoenixSuccessor), (c:UkAppointment)
      WHERE c.officerId = b.officerId
        AND b.companyStatus = 'dissolved'
        AND c.appointedOn > b.appointedOn
      WITH c, max(coalesce(b.phoenixDepth, 1) + 1) AS d
iffA node carries the label if and only if some rule concludes it. Rules are UNORDERED clauses — reordering changes nothing.
unionMany rules, one definition. Two rule sets may even derive the same label: that is more clauses, not a conflict.

Every conclusion carries its why

Each member records its firing chain — which rule, which round, which values, and how values grew. An explanation is READ off the chain, never reconstructed after the fact.

blocked(Baltic Shipping)
  ⇐ rule 2, round 2: blockedStake 50
    via Meridian Holdings (blocked)
      ⇐ rule 2, round 1: blockedStake 55
        ⇐ Ivanov 30% + Petrov 25%, both listed
goneConclusions are computed, never stored. Nothing persists after the query; removing the realm removes the label with nothing to clean.
scopedRule bodies pass the same per-user scope rewriting as every query. A rule can never read what its author's own query could not.

Where a view ends, a rule begins

A view saves ONE query and cannot reference itself. A rule set is many clauses of one definition, and may. Same no-new-grammar stance: usage is a plain label, definition is metadata.

ViewRule set
Bodyone query, with RETURNmany bodies, no RETURN — the head projects
Self-referenceneverthe point
Yieldsrows / membershipmembership + derived properties + why
pairShip the projection VIEW with the rule set — referencing the label is what triggers evaluation, and the view is how every surface reaches it.
Writing a rule set A head names what the rule concludes; a body says when.

The head — derive:

One node pattern: a variable (which body binding becomes the member), exactly one label (the set's own derives), and optional properties computed from body bindings.

derive: "(e:Blocked {blockedStake: stake})"
quoteAlways quote the head: property maps contain : , which YAML silently reads as a nested mapping. Same trap for bodies — use a block scalar (from: |).
namePrefix derived property names for the realm (phoenixDepth, not depth) — the label's vocabulary outlives the file.

The body — from:

Ordinary read-only Virtual Cypher that BINDS variables and stops. No RETURN — the head is the projection, and the host constructs the runnable query from the parsed head.

from: |
  MATCH (o:Blocked)-[r:OWNS]->(e:OwnershipEntity)
  WITH e, sum(r.pct) AS stake
  WHERE stake >= $minStake
dataRules conclude over data PRESENT in the graph. A producer-backed realm feeds rules through promoted/stored anchors — say the data contract in the description.
composeA body may match real labels, virtual labels, views — anything a query may. The VC sheet's rules apply inside a body unchanged.

Params — same vocabulary as views

Declared with type / default / description, referenced as $name in any body. A query that merely MATCHes the label evaluates on DEFAULTS — so default everything meant for implicit use.

params:
  minStake:
    type: int
    default: 50
    description: "Aggregate % at which status propagates"
anchorAnchoring a rule set to one entity is just declaring its key: {officerId: $officer}.
neverA param named userId / worldId or an engine-reserved word — a rule param can never shadow scope.
Why a rule set is refused Every refusal is a leg of the termination guarantee.

The validated fragment

Rules can only label nodes that exist, membership only grows, and a growing subset of a finite set must stop growing. Each refusal protects one of those facts.

RefusedBecause
Writes in a body (CREATE/MERGE/SET…)the universe must stay finite
The derived label under NOTa new member could falsify an old conclusion
min/avg/percentiles inside recursionthey can shrink as membership grows; sum/count/max/collect cannot
RETURN in a bodythe head is the projection
An undeclared $paramrefused at install, not at first evaluation
A head that is a path, unlabelled, or variable-lessa rule concludes exactly one node
loudRefusals name the rule and the property it broke, at validate/install time. A rule set never half-installs, and a fixpoint that cannot converge fails loudly, never truncates.
Using a derived label It is just a label. That is the whole interface.

MATCH it, join it, test it

The label composes like any other — in patterns, as a per-row boolean, joined against base edges. Referencing it is what triggers evaluation.

MATCH (p:PhoenixSuccessor) WHERE p.phoenixDepth >= 2
WITH DISTINCT p.officerId AS officer
MATCH (all:UkAppointment {officerId: officer})
RETURN officer, all.companyName,
       (all:PhoenixSuccessor) AS flagged
viewThe shipped projection view is the front door: PhoenixSuccession(minDepth) reaches the console, apps and the SQL door with no client work.

Try it before you ship it

The ad-hoc door takes a rule set and a query in one call, and answers with the rows PLUS each member's firing chain. Invalid rules come back as a 400 carrying the validator's exact sentence.

POST /api/v1/admin/kg/derive
{ "derives": "Blocked",
  "rules": [ { "derive": "…", "from": "…" } ],
  "paramSpecs": { "minStake": { "type": "int", "default": 50 } },
  "params":     { "minStake": 65 },
  "cypher": "MATCH (e:Blocked) RETURN e.name" }
ladderAd-hoc first, artifact when it earns a name — exactly as raw Cypher graduates to a saved view.
joinIn the response, derived[].derivations[].elementId correlates traces to rows — RETURN elementId(x) to join them.
